# Existing PostgreSQL data transfer

Changing `.env` does not move records. If this is a fresh deployment with no records to retain, initialize the new MariaDB database normally. If any existing owner, content, media, inquiry, aggregate, audit, queue or token records must remain, transfer them before cutover. This task has not inspected the user's existing `.env` or databases and cannot determine which records are valuable. Existing databases and volumes are preserved.

The original PostgreSQL baseline is frozen under `backend/tests/Fixtures/postgres/` **only** for isolated transfer tests. Normal migrations now create MySQL/MariaDB tables. Never run these edited baseline migrations against an existing PostgreSQL database. Provision a separate, empty destination; preserve the source and prior application revision for rollback.

## Snapshot, copy and reconcile

1. Inventory the source privately. Record counts, DB version, encoding, media disk/key layout, database size, timestamp ranges, queued/failed jobs and token expiry. Keep a tested encrypted PostgreSQL backup (`pg_dump` using a private credential file), all media variants/private pending inputs, and the existing APP_KEY. Do not commit backups, payloads or credentials. Confirm the destination has sufficient database/disk/packet capacity.
2. Freeze **all** source writers: put the old API in maintenance, stop cron/scheduler/workers, and wait for in-flight requests/jobs. Take matching database/media snapshots. Keep the destination API and cron offline. The command uses a repeatable-read, read-only source transaction, but it cannot prevent another process from writing later; the operational freeze is required through final reconciliation/cutover. Prefer a read-only PostgreSQL role.
3. On a private migration machine with PHP 8.5, **both** PDO PostgreSQL and PDO MySQL, the locked app dependencies and network access to both databases, configure DB_* for the new MariaDB/MySQL destination. Set temporary TRANSFER_PG_HOST/PORT/DATABASE/USERNAME/PASSWORD and TRANSFER_PG_SSLMODE for the source using a secure environment manager; TLS defaults to require. Do not install PDO PostgreSQL on the shared production host merely for normal runtime. Source values use the separate `legacy_pgsql` connection and never reuse the destination DB_DATABASE.
4. Migrate the **new empty destination only** with `php artisan migrate --force`. Do not seed it yet; the importer refuses existing settings as well as other domain/runtime rows. MySQL DDL is not transactionally reversible; a failed schema setup is repaired/recreated only on the new disposable destination, never the original source.
5. Run `php artisan app:transfer-postgres` for the default read-only source inventory. It emits table counts and canonical SHA-256 hashes, never field values or passwords. Save reports privately. Check the listed table inventory and confirm the exact target database name.
6. Run `php artisan app:transfer-postgres --apply --confirm-target=EXACT_NEW_DATABASE`. This explicit mode copies all 21 domain/runtime tables in parent-first order, preserving IDs, hashes, nulls, Unicode, microsecond UTC dates, JSON object/array semantics, relationships and counter keys. MySQL generates its internal constant owner_slot; it is not read from PostgreSQL. Migration history and application_locks are new engine-specific state, not copied. The source transaction is always rolled back (read-only). The target's data copy and reconciliation share one InnoDB transaction with foreign keys/checks enabled; no truncation, FK disabling or updates to existing records occur. A target transfer-row lock serializes concurrent import attempts. Explicit IDs advance AUTO_INCREMENT; verify the next created record in staging.
7. Each copied table is reconciled before commit using row counts and canonical hashes over primary-key order. JSON object keys are sorted; arrays retain order; timestamps normalize to UTC with microseconds; integers/booleans normalize consistently. Any mismatch/constraint/import failure rolls back destination data. MySQL AUTO_INCREMENT values can still advance after rollback; this does not change source data or require resetting production IDs. A nonempty destination refuses a second import. Correct errors on a new empty destination and repeat from the frozen source; do not force overwrite.
8. While both systems remain frozen, run `php artisan app:transfer-postgres --verify`. This mode compares existing destination data with the current source without inserting. A mismatch fails the command. Reconcile rows/counts plus independent business totals and media references. Copy media using private rsync/archive/S3 operations preserving storage keys; compare SHA-256 checksums of every copied file and check ready-image URLs. The database importer does **not** transfer media bytes, APP_KEY, `.env`, TLS configuration, cron, host logs or database roles.
9. Cache/cache_locks and queued/failed/batched jobs are copied as stored values; stop all old processes before the snapshot. Review stale distributed cache lock TTLs, reserved jobs and failed-job retry policy before resuming. Queue payloads contain IDs; pending private inputs must also be copied. Personal access-token hashes/expiry are preserved, so existing client sessions can continue with the same owner/APP_KEY; intentionally revoke them only as a separately approved operational decision. No plaintext tokens/passwords are exported by the tool.
10. Seed singleton defaults safely **after** the import (existing settings remain), cache destination configuration/routes, then test owner login, enabled/disabled behavior, authenticated content/media/inquiry/report flows, literal search, pagination, public visibility, token revocation and a complete upload/process/public-image cycle in isolated staging. Use the unchanged shared-client smoke script against disposable loopback staging. Validate the public responses against the unchanged OpenAPI contract. Run a fresh backup/restore rehearsal before authorizing production cutover.
11. With explicit deployment authorization, point only the API at the new destination, verify `https://api.mahmoudbannan.com`, then resume the new scheduler/finite queue cron. Retain the original database/media/backup offline until acceptance. If rollback is required before new writes, restore routing/config to the untouched old installation. After new destination writes, rollback needs a planned reverse reconciliation; switching back blindly loses those writes. Never run destructive migrations or drop the source as part of cutover.

The source snapshot transaction stays open for the transfer; use a migration machine with an appropriate execution window and confirm Hostinger's query/account quotas. The tool streams 100 rows per page and inserts individual rows, avoiding large packets. It is intended for this known schema, not a general PostgreSQL dump converter. Large installations require a measured staging rehearsal and a maintenance window; no throughput guarantee is claimed.

## Executable rehearsal

`PostgresTransferTest` exercises the real original PostgreSQL schema and the new real MySQL/MariaDB schema. It creates only fictional rows in an explicitly named `*_testing` source and target. Set TRANSFER_TEST_SOURCE=1 only for that isolated test source. First prepare its legacy schema:

```sh
# DB_* already names a separate disposable *_testing MySQL/MariaDB target.
# TRANSFER_PG_* names another disposable *_testing PostgreSQL database.
php artisan migrate --database=legacy_pgsql --path=tests/Fixtures/postgres --force
TRANSFER_TEST_SOURCE=1 php artisan test --filter=PostgresTransferTest
```

The test covers dry-run non-mutation, transfer/reconciliation of all tables, nonempty-target refusal, original IDs, password hashes, microsecond timezone conversion, JSON fields, nullable analytics, relationships and next-ID allocation. The complete CI matrix also enables this rehearsal. See [actual execution results](mysql-migration-completion.md) for executed checks and remaining gates; CI configuration alone is not evidence of a passing hosted run.
