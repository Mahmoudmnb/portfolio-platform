# Contributing

Thanks for helping improve Portfolio Platform. Start with the root README and the documentation for the area you want to change. For substantial behavior or architecture changes, open a focused proposal before investing in a large pull request.

## Set up safely

Fork the repository, create a topic branch, and follow [backend setup](docs/development.md) and/or [dashboard setup](docs/dashboard-development.md). Use the versions in manifests, lockfiles and CI. Install from lockfiles; do not update unrelated dependencies.

Use fictional data and your own local API. Never point tests, smoke scripts or experimental clients at the author's production service. Database integration tests require an isolated MySQL/MariaDB database with a name ending in `_testing`; PostgreSQL is needed only for the explicit legacy-transfer test lane. Read scripts' disposable-environment guards before running them.

Do not submit `.env`, tokens, owner passwords, uploaded content, inquiry messages, signing keys, database backups or raw production logs. Sanitize screenshots and error reports. The published API URL is public configuration, but it is not permission to administer or test the live service.

## Find your area

- backend/: Laravel API behavior, migrations, resources, policies and jobs.
- dashboard/: Flutter UI, session state, media flow and Android configuration.
- packages/portfolio_api/: pure Dart transport, request encoding and response parsing.
- website/: reserved Jaspr integration; discuss work before introducing an application.
- docs/: setup, API contracts, operations and verified evidence.

Read applicable AGENTS.md files if using a coding assistant. Keep changes focused and preserve unrelated work. Shared client code must remain independent of Flutter and secure-storage implementation.

## Checks

For backend changes, from backend/ with a disposable test database:

```sh
composer install
vendor/bin/pint
vendor/bin/phpstan analyse --memory-limit=512M
php artisan test
composer audit --locked
python3 ../scripts/check-openapi.py
```

The contract checker needs the Python requirements and response fixtures generated by the tests; see [development setup](docs/development.md). Never run destructive migration commands against existing content.

For shared client changes, from packages/portfolio_api/:

```sh
dart pub get --enforce-lockfile
dart analyze --fatal-infos
dart test
```

For dashboard changes, from dashboard/:

```sh
flutter pub get --enforce-lockfile
flutter analyze --fatal-infos
flutter test
```

Run dart format on changed Dart files. Check ordinary Android builds for native/configuration changes, supplying a local API_BASE_URL. A hosted build does not prove device execution. For contract changes, regenerate models using packages/portfolio_api/tool/generate_contract.py, format the output and review its diff. Coordinate intentional API changes with both clients and update docs/openapi.yaml and integration examples.

Documentation/configuration-only changes need link/schema/whitespace checks rather than unrelated runtime suites. Run git diff --check. Report unavailable checks honestly and include commands/results in the pull request. Do not use skipped checks as passing evidence.

## Pull requests

Explain the concrete problem, resulting behavior, affected area, verification and relevant limitations. Add fictional screenshots for UI changes and behavior-focused tests for meaningful fixes. Keep generated outputs consistent with their sources. Do not include unrelated formatting, dependency upgrades, live deployment edits or secret files.

A maintainer reviews before merging; contributors do not need access to production or signing credentials. Dependency update PRs receive the same review as other code. No contributor license agreement or mandatory sign-off is currently required; contributed source is covered by the repository's existing license. Preserve third-party licenses and only contribute material you have permission to share.

For security reports use [SECURITY.md](SECURITY.md). For bugs and proposals use the GitHub issue templates. Please follow [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).
